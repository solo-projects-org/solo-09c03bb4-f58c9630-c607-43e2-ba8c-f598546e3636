# 景区客流报表补仓 API

旧日报缺页后，用留存的**跨日客流报表**补齐日明细的 FastAPI 服务。
SQLite 留存现行报表，提供整批补录、**整批归档**、冲突整批退回、日人次唯一值查询。

## 业务规则

- 每份报表含：编号、首天、末日（均计入）、档期总人次、状态（在线 / 归档）；日人次为非负整数。
- 单份报表档期（末−首+1）**最长 90 天**；库内报表**最多 120 份（含归档件）**。
- 支持成批补录；已有编号按**整份替换**处理（档期、总量、版本整体更新），
  同号更正后的报表一律**转为在线**。
- 每批都与**入库时已生效的在线及归档报表**一起核对：
  - 能同时成立才整体提交（单事务，失败回滚，不会出现半批入库）；
  - 无法同时成立则**整批退回**（HTTP 409），返回一组冲突报表编号，
    该组是**最小冲突组**——去掉组内任一份后，组内其余报表即可自洽。
- **归档**（`POST /reports/archive`，提交一批在线报表编号）：
  - 只有**移出整批后**，剩余在线报表仍能**唯一推出每份原件的档期总人次**，
    整批才会转为归档；条件不成立时整批拒绝（HTTP 409），
    响应列出**无法推出总量的报表编号**，失败请求不改变任何报表状态；
  - 归档原件留档备查（`GET /reports` 标明 `online` / `archived`），
    但**不参与在线求解与查数**；
  - 查日明细（`GET /daily`）只用同一套**已提交的在线报表**。
- **补录与归档交错**：所有判断按请求提交时的数据快照进行；补录成功后按
  补录后的在线报表重新核对每份归档件，**失去唯一依据的归档原件随补报
  恢复在线**（响应 `restored_ids`），其余继续归档。
- 更正/替换报表后，失去唯一依据的日人次会自动转回待补（查询按在线报表实时求解）。

## 算法要点

把报表总和约束转成**差分约束系统**：

- 令前缀和 `P_d = 首天..d 的累计人次`，锚点 `P_0 = 0`；
- 报表 `[s,e] 总量 t` 等价于 `P_e - P_{s-1} = t`（拆成 `>=t` 与 `<=-t` 两条边）；
- 日人次非负等价于相邻前缀点之间 `P_d - P_{d-1} >= 0` 的权 0 链边。

图中只放报表端点（压缩图，节点 ≤ 241），用 numpy Floyd-Warshall 求全源最长路：

- 对角线出现正值 ⇔ 存在正权环 ⇔ 报表集合不可行；
- 对每个被覆盖日期，由最长路/最短路推出当日人次的最小值与最大值，
  两者相等且有限即为唯一确定；整数边权保证结果为整数。
- **归档判定**：区间 `[s,e]` 的总量即 `P_e - P_{s-1}`，其下界为最长路
  `L[s-1][e]`、上界为反向最长路取负 `-L[e][s-1]`；双向可达且上下界相等
  即为“可由剩余在线报表唯一推出”。整批候选的端点一次性注入同一张压缩图，
  一次 Floyd-Warshall 批量判定。
- 冲突组用删除法求最小不可行子集（IIS）：逐个尝试删除，删除后仍不可行的成员不是必要成员。

## 目录结构

```
app/
  main.py       FastAPI 路由（/docs 即 Swagger）
  schemas.py    请求/响应模型
  service.py    业务服务：整批原子提交、归档判定、容量护栏、冲突诊断、求解缓存
  solver.py     差分约束求解器（纯函数，含区间总量可推出性判定）
  database.py   SQLite / SQLAlchemy 持久化（含旧库 status 列自动迁移）
tests/          pytest：单元、随机暴力校验、属性测试、API 集成、归档场景、规模压测
Dockerfile / docker-compose.yml
```

## 用 Docker Compose 启动

```bash
docker compose up --build
# 服务：http://localhost:8000
# Swagger：http://localhost:8000/docs  （根路径 / 会自动跳转）
# 健康检查：http://localhost:8000/health
```

SQLite 数据文件落在命名卷 `scenic-data` 的 `/data/scenic.db`（WAL 模式），
容器重建后数据保留。旧版（v1.0）数据库启动时自动补 `status` 列，
存量报表默认视为在线。

## Swagger 操作示例

1. `POST /reports/batch` 补录第一批拼图报表：

   ```json
   {"reports": [
     {"report_id": "A1", "start_date": "2024-03-01", "end_date": "2024-03-03", "total": 6},
     {"report_id": "A2", "start_date": "2024-03-01", "end_date": "2024-03-02", "total": 4},
     {"report_id": "D",  "start_date": "2024-03-03", "end_date": "2024-03-03", "total": 2}
   ]}
   ```

2. `GET /daily?start_date=2024-03-01&end_date=2024-03-03` 查数：
   3 月 3 日唯一为 2，其余日期 `pending`。
3. `POST /reports/archive` 归档 D（A1−A2 仍能唯一推出 x3=2）：

   ```json
   {"report_ids": ["D"]}
   ```

   成功后 `online_count=2, archived_count=1`；再查 `/daily` 结果不变（查数只用在线报表）。
   若提交一份无在线依据的独立报表编号，得到 `409`，响应体
   `detail.non_derivable_report_ids` 即无法推出总量的编号，报表状态不变。
4. `GET /reports` 查原件，每份带 `status`（`online` / `archived`），
   可用 `?status=archived` 只看归档件。
5. 把 A2 同号更正为 `2024-03-02` 单日总量 0：D 的唯一依据失效，
   补录响应 `restored_ids=["D"]`，D 随补报恢复在线；同号更正归档件本身
   也会直接转在线并递增 `version`。
6. 再补一份与现行（含归档）报表矛盾的报表会得到 `409`，响应体
   `detail.conflict_report_ids` 即最小冲突组；同批其它报表随整批退回，不会入库。

## 接口一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/reports/batch` | 整批补录（替换/新增，同号转在线），冲突 409 整批退回 |
| POST | `/reports/archive` | 整批归档在线报表；不可推出总量时 409 并列编号 |
| GET  | `/reports` | 列出报表原件（带在线/归档状态，可 `?status=` 过滤） |
| GET  | `/daily` | 区间查数（只用在线报表），缺省区间覆盖全部在线报表范围 |
| GET  | `/health` | 健康检查 |

## 本地自测

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt
SCENIC_DB_PATH=/tmp/scenic.db .venv/bin/pytest -q
SCENIC_DB_PATH=/tmp/scenic.db .venv/bin/uvicorn app.main:app --port 8000
```

测试包含：

- 求解器单元测试（可行性、唯一确定、零总量、嵌套/交错区间、同编号替换、
  **区间总量可推出性与不可达边界**）；
- 60 组随机小实例的**暴力穷举校验**（枚举所有非负整数日向量核对可行性与逐日界）；
- 200 组随机实例的最小冲突组删除性质；
- API 集成测试（原子回滚、容量上限含归档件、替换后版本与待补回转、
  **归档成功/整批拒绝/补录恢复/归档件参与冲突验算/旧库迁移**、持久化视图）；
- 120 份 × 最长 90 天的规模压测（单次求解约 15ms，冲突诊断约 0.6s）。
